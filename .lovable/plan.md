# Automated SEO blog pipeline (n8n + Google Sheet → HQ Stones)

## Recommendation (short)

Use the **database (Lovable Cloud)**, not the repo, for new articles. This site already renders every page on the server (SSR), so an article pulled from the database at request time reaches Google as full HTML, with title, canonical and schema, just like a hardcoded one. Nothing gets rebuilt, and Lovable doesn't have to edit anything per article: n8n calls one secured endpoint and the article is live within seconds.

Repo/static content is only "safer" for sites with no SSR (pure SPA), where Google would get an empty page. That doesn't apply here. Committing through GitHub also means a rebuild and publish for every article, which is brittle and slow to automate.

## Current state (verified)

- Articles are hardcoded: `src/data/blog.ts` holds the metadata (slug, dates, cover, author), and the text lives in the 4 locale files (`blog.posts.<key>.*`).
- `BlogPost.tsx` and `blog.$slug.tsx` only find posts in `BLOG_POSTS`. An unknown slug returns 404.
- `public/sitemap.xml` is a static file generated by a script from the repo data, so it can't see new articles.
- There's already a `seo_content` table plus an admin panel, but it only overrides existing posts. It can't create new ones.
- Language: one canonical URL per page (hreflang was removed on purpose). Each automated article should therefore be written in **one language**, and that language becomes the page's language.

## Changes this project needs

1. **New `blog_posts` table**: slug (unique), lang, title, meta_title, meta_description, excerpt, body_md, sources (json), internal_links (json), hero_image_url, hero_alt, author_key, status (draft/published), published_at, updated_at, plus a `site` column so all 3 sites can share the same schema. Public read covers only rows that are `published` with `published_at <= now()`. Writes happen only through the server.
2. **Secured intake endpoint** `POST /api/public/blog/upsert`: an HMAC signature or a shared secret in a header, Zod validation, upsert by slug, and slug normalization. The hero image is either an absolute URL or downloaded into Cloud storage (safer long term). It returns the final URL.
3. **Article page**: the `blog/$slug` loader checks the static posts first, then the database, all server-side. If neither has it, it returns a real 404. `head()` builds the meta title/description, the canonical `https://hq-stones.com/blog/<slug>`, og:image (absolute URL) and og:locale from the article's language.
4. **Rendering**: reuse the current layout (H2/H3, sources, author block, related posts). The Markdown is sanitized and has no raw HTML. Internal links are rendered as real `<a href>` links. JSON-LD BlogPosting includes headline, dates, author, image, inLanguage and mainEntityOfPage.
5. **Blog list**: merges static and database posts, sorted by date, also loaded server-side.
6. **Dynamic sitemap**: a server route `/sitemap.xml` covering static pages, products and all posts (static + database), with `lastmod`. The static `public/sitemap.xml` is removed so it doesn't take precedence. `robots.txt` stays unchanged.
7. **Freshness**: a short cache (for example 5 min, with stale-while-revalidate) on article and sitemap responses. An optional ping of the sitemap to Google Search Console from n8n after publishing.
8. **Tests**: the endpoint rejects bad signatures, an unknown slug returns 404, a published post appears in the sitemap and has valid JSON-LD.

## n8n flow (outside Lovable)

```text
Google Sheet row (status=ready)
  -> n8n: build JSON, sign with secret
  -> POST https://hq-stones.com/api/public/blog/upsert
  -> write returned URL + status=published back to Sheet
  -> (optional) GSC sitemap resubmit
```
The same workflow serves all 3 sites. Only the base URL and secret change per site. Each site needs these same changes (a shared table schema and endpoint contract).

## What you need to provide

- One secret per site (added in Secrets), shared with n8n.
- Decide: should the hero image be hosted by us (recommended) or just linked?
- Decide: do automated posts publish directly, or go to draft for review in the existing admin panel?

## Technical notes

- Loader reads use a server-side public client with a narrow published-only read policy. The endpoint uses the admin client only after verifying the signature.
- Scheduled posts (`published_at` in the future) stay hidden and appear automatically once their date passes, with no cron needed.
- The existing hardcoded posts stay as they are, so nothing breaks.
